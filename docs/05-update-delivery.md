# 05 — The `ryoku` control CLI and the update/delivery contract

Scope: the Go program `ryoku/cli/` (dispatcher `main.go`, `internal/updater`,
`internal/doctor` with all 118 registered reconcilers, `internal/sys`,
`internal/ryotunesrelease`, `internal/ryokumanifest`, `internal/keyring`,
`internal/securitykey`, `internal/keyboard`, `internal/importer`, `track.go`,
`recovery.go`, `wm.go`, `plugin*.go`), the delivery contract in
`docs/updates.md` / `docs/cli.md` (and `docs/profile.md`, which has no CLI
surface), `bin/ryoku-dev-verify-delivery`, the CLI's Go tests, and
`release/packages/ryoku/PKGBUILD`. Source pinned at
`98a0368253d9628be72b853985878a5db90e1547`. Every `path:line` below is relative
to the Ryoku repo root. Debian versions come from `tools/pkgver` (trixie /
trixie-backports / forky / sid / Ubuntu 26.04 resolute) and packages.debian.org
file lists, queried 2026-10-17.

The CLI is a dispatcher over pacman, yay, snapper, limine and git. Debian has no
pacman, no yay, no AUR, no limine, no snap-pac, no limine-snapper-sync, and no
grub-btrfs (all five checked against `sources.debian.org/api/search`, see §6).
This document specifies the retool.

## 1. Subcommands, step by step

`main.go:40-97` dispatches; it first scrubs the Quickshell crash env
(`main.go:41`, `crashenv.go:12`) and loads the catalog from
`/usr/share/ryoku/i18n` (`main.go:42`). Two "worlds" (`docs/cli.md:8-24`): a
**packaged** box (no checkout; `sys.ResolveRepo()` returns "") and a
**checkout** box (`RYOKU_REPO`, or the path `deploy.sh` recorded in
`~/.local/state/ryoku/repo`, or a `~/ryoku-arch` clone when a `RYOKU_CHANNEL` is
tracked: `internal/sys/repo.go:28-51`).

### 1.1 `ryoku update [--system|--full] [-v] [--channel-switch]` (`main.go:49`)

**What it does** (`internal/updater/update.go:78-258`, stage 2 `594-791`):

1. Flags: `--stage2 <pre>` (`update.go:79`), `-v/--verbose` raw output
   (`83-85`), `--channel-switch` (`86-88`, set only by `track`/`rollback --to`
   via `release.go:196`), `--system`/`--full` (`89-91`).
2. Exclusive non-blocking `flock` on `$XDG_RUNTIME_DIR/ryoku-update.lock`
   (`97-103`, `268-279`).
3. Refuses below 1 GiB free on `/` (`111-114`, `284-291`).
4. Caches sudo once on a TTY (`sudo -v`, `311-316`) and refreshes it every
   minute (`sudo -n -v`, `324-342`).
5. Picks the step list: checkout → `gitSteps`, `--system` → `systemSteps`, else
   `pkgSteps` (`124-132`, lists at `29-61`); progress is published to
   `$XDG_RUNTIME_DIR/ryoku-update.json` (`runstate.go:73-78`).
6. Pre snapshot:
   `sudo snapper -c root create -t pre -c number -p -d "ryoku-update (from <sha>)"`
   (`134-136`, `1789-1807`, description `347-358`); skipped with a note when
   snapper or `/etc/snapper/configs/root` is missing.
7. **Checkout lane** (`140-160`): `channelUpdate` (`channel.go:112-140`: bounded
   `git fetch origin <ch>` `224-230`; `syncChannel` fast-forwards a clean tree,
   resets a diverged channel branch, leaves a dirty tree `172-212`; runs
   `<repo>/ryoku/shell/deploy.sh` `136`), then `rashinReindex` (`1035-1048`),
   `prowlRefresh` (`1055-1071`), `upgradeRyotunes` (`ryotunes.go:26-44`),
   `offerSnapperHelpers` (`1160-1189`), `runFreshDoctor`
   (`/usr/bin/ryoku doctor`, `1215-1221`), post snapshot (`1809-1819`),
   `finishRun` (`582-587`).
8. **Packaged lane** (`162-257`):
   1. exports `RYOKU_UPDATE_FROM` from `/etc/ryoku-release` (`165-167`);
   2. deletes `/var/lib/pacman/db.lck` when no `pacman` process runs (`168`,
      `1104-1114`);
   3. `sudo pacman -Sy --noconfirm` (`-Syy` on a channel switch) (`175`,
      `ryokuset.go:213-219`);
   4. builds the Ryoku set: `pacman -Slq ryoku` ∩ `pacman -Qq`, minus
      `ryotunes`, repo-qualified `ryoku/<name>` (`178`, `ryokuset.go:54-106`);
      on an ordinary update drops every name whose installed version is newer
      than the repo's, via per-name `pacman -Qi <n>` and `pacman -Si ryoku/<n>`
      and `vercmp` (`ryokuset.go:134-190`);
   5. on a channel switch removes `ryoku-desktop-hyprland`/`-niri` with
      `pacman -Rdd` when the target repo does not serve them (`184-191`,
      `455-482`);
   6. zero-set handling (`197-212`); otherwise runs, sleep-inhibited,
      `sudo env SNAP_PAC_SKIP=y RYOKU_MANAGED_UPDATE=1 pacman -S --needed --noconfirm --overwrite <ryokuOverwriteGlob> ryoku/<pkg>...`
      (`214`, `364-366`, `ryokuset.go:233-237`, glob `update.go:512-518`),
      scraping "exists in filesystem" paths (`upgradelog.go:92-163`);
   7. on failure `healPackageUpgrade` deletes conflict paths no package owns
      (`pacman -Qo`, `486-499`) or, when the error names the database, drops the
      cached `[ryoku]` sync db (`421-448`, `sys/release.go:169-186`); it is
      called twice in a row (`215`, `220`) before one retry (`221-231`);
   8. system lane: `pacman -Qu` minus the set (`239`, `ryokuset.go:243-261`);
      `--system` runs `runSystemLane` (`372-399`:
      `sudo env SNAP_PAC_SKIP=y RYOKU_MANAGED_UPDATE=1 pacman -Syu --noconfirm --overwrite <glob>`
      `524-527`; `yay -Sua --noconfirm` `538-540`;
      `flatpak update --noninteractive --assumeyes` `547-561`), otherwise prints
      "take them with `sudo pacman -Syu`" (`404-410`);
   9. `syscall.Exec("/usr/bin/ryoku", "update --stage2 <pre> [--system]")`
      (`248-257`) so the new binary runs stage 2.
9. **Stage 2** (`594-791`): re-primes sudo; arms the boot guard (`628`,
   `bootguard.go:70-91`); `ensurePackagePowerCutover` runs
   `sudo /usr/bin/ryoku-power-cutover package` when
   `/var/lib/ryoku/power-cutover-hook-active` is absent (`817-841`); reads
   login1 sessions over D-Bus (`636`, `1993-2044`); takes the power-cutover
   flock (`643`, `793-808`); starts a user-scope
   `systemd-run ... systemd-inhibit --what=sleep sleep infinity` guard and
   verifies it via `org.freedesktop.login1.Manager.ListInhibitors` (`653`,
   `871-923`); `sudo systemctl reload systemd-logind` (`662`, `1025-1030`);
   stops `ryoku-clamshell`/`ryoku-idle` (`666`, `947-957`);
   `ryoku-power-cutover generation-guard-start` (`674`); stops the shell (`683`,
   `1887-1934`: `systemctl --user stop ryoku-shell`, `ryoku-shell quit`, `pkill`
   of quickshell configs, livewall, hub); pauses compositor auto-reload (`695`,
   `1823-1828`); **`Materialize()`** (`696`); re-renders the provider config
   from `~/.config/ryoku/desktop.json` (`712`, `1857-1864`); `session-bind`,
   reload, `startShell` (`1940-1966`), `waitForShellReady` (`2046-2068`),
   `activatePowerPolicy` (`970-1013`), `restartWallpaper` (`2076-2092`),
   `session-check`, `generation-guard-stop`, guard release (`715-778`);
   rashin/prowl/ryotunes (`779-781`); snapper helper offer + `ryoku doctor`
   (`784-785`); post snapshot
   `sudo snapper -c root create -t post --pre-number <pre> -c number -d ryoku-update`
   then `sudo snapper -c root cleanup number` (`788`, `1809-1819`).

**Arch couplings:** pacman everywhere in step 8 (cites above); `vercmp`
(`ryokuset.go:180`); `/var/lib/pacman/db.lck` (`update.go:1105`); pacman output
grammar (`upgradelog.go:36-39,147-163,514-552`); `SNAP_PAC_SKIP` (snap-pac's
variable, `ryokuset.go:234`); `yay` (`update.go:378-386,538-540`);
`snap-pac`/`limine`/`limine-snapper-sync` package probes and
`ryoku-pkg-add`/`ryoku-pkg-aur-add` installs (`1127-1189`); user-facing strings
naming pacman/Arch (`update.go:409,1259,1508`, `bootguard.go:179`; all are i18n
keys present in every catalog under `ryoku/i18n/catalog/`).

stage 2 (minus helper offers) are distro-neutral.

**Port steps:** see §7 (code plan). Command-level mapping:

### 1.2 `ryoku status [--json]` (`main.go:61`, `update.go:1473-1524`)

**What it does:** prints config base, channel, release (`/etc/ryoku-release` vs
the channel's `release.json`), installed/available, behind count, the system
lane count ("`sudo pacman -Syu`", `1507-1511`) and the snapshot count in three
states (`1515-1522`). `buildStatus` (`1572-1581`) = `baseStatus` (`1585-1599`:
checkout → `channelStatus` `channel.go:72-107` with `git fetch`,
`rev-list --count`, `log`; packaged → `sys.InstalledVersion()` +
`latestAvailable("ryoku-desktop")` = `pacman -Sl ryoku` (`1675-1688`) overridden
by `checkupdates` (`1593-1597`, `1701-1720`), then `packagedStatus`
(`1605-1649`) with GitHub compare/commits lookups (`commits.go:63-135,191-260`
against `ryoku-dev/ryoku-arch`, `commits.go:29-34`)) + `systemPackageUpdates` =
`checkupdates` + `yay -Qua` (`1724-1745`) + `addRyotunesUpdate`
(`ryotunes.go:50-60`). `--json` emits `statusReport` (`1530-1556`); the shell
daemon polls it (`ryoku/shell/ipc/updates.go:71`), the Hub renders it
(`ryoku/hub/quickshell/Singletons/Updates.qml:6-26`).

**Arch couplings:** `pacman -Sl ryoku` (`1676`); `checkupdates` from
pacman-contrib (`1703-1711`, a private-db sync, no root); `yay -Qua`
(`1731-1736`); `shortCommit` expects `<core>.r<count>.g<sha>-<rel>`
(`1655-1662`), produced by `bin/ryoku-release-version:30-43`.

**As-is on Debian:** NO.

**Port steps:**

1. `latestAvailable` → served version of `ryoku-desktop` from the Ryoku Packages
   index (same parser as §1.1) or `apt-cache madison ryoku-desktop`
   (`ryoku-desktop | <ver> | <uri> ./ Packages`, filter by the Ryoku URI).
2. `pendingUpdates` (checkupdates) → either (a) a private apt tree, no root:
   `apt-get -o Dir::State::Lists=$XDG_CACHE_HOME/ryoku/apt/lists -o Dir::Cache=$XDG_CACHE_HOME/ryoku/apt/cache -o Debug::NoLocking=1 update`
   then `apt-get -o Dir::State::Lists=... -o Dir::Cache=... -s full-upgrade`
   (the same technique `chdist` from devscripts uses), or (b) system lists kept
   fresh by apt's own timer: ship `/etc/apt/apt.conf.d/10ryoku-periodic` with
   `APT::Periodic::Update-Package-Lists "1";` (apt-daily.timer), then parse
   `apt-get -s full-upgrade` unprivileged.
3. `aurUpdates` → delete (§5).
4. Keep the `statusReport` JSON keys byte-identical (`installedVersion`,
   `latestVersion`, `available`, `pendingUpdates`, `updates`, `recent`,
   `channel`, `snapshots`, `snapshotsKnown`, `packages`, `systemUpdates`,
   `release*`): the shell daemon and Hub depend on them.
5. Replace the "`sudo pacman -Syu`" strings (`update.go:1508`,
   `ryoku/hub/quickshell/pages/UpdatesPage.qml:595`) with
   `sudo apt full-upgrade`.
6. `ryokuRepoSlug` default (`commits.go:33`) → the port's GitHub repo, or set
   `RYOKU_REPO_SLUG`; the packaged version string must keep the `.g<sha>` token
   of that repo's commit for the compare to resolve.

**Complexity:** Medium.

### 1.3 `ryoku rollback [--to <tag> | <id>]` (`main.go:55`, `update.go:1238-1330`)

**What it does:** `--to v<tag>` validates the tag (`sys.IsReleaseTag`,
`internal/sys/release.go:47-53`) and calls `Track(tag)` (`1246-1252`) — the
Ryoku set moves to the frozen release, Arch untouched. `<id>` prints the
boot-menu restore guide (`restoreGuide` `1306-1330`: "reboot, open Limine
Snapshots → id, run `sudo limine-snapper-restore`", and if `limine-snapper-sync`
is missing tells the user to run
`ryoku-pkg-aur-add limine-snapper-sync && sudo systemctl enable --now limine-snapper-sync.service`).
No argument: `printReleases` (`1273-1302`, ledger
`<RepoBase>/releases/index.json` via `release.go:59-107`) and `Snapshots()`. The
rationale (`1231-1237`, `docs/cli.md:81-87`): the root is pinned
`rootflags=subvol=@`, so `snapper rollback` (which flips the btrfs default
subvolume) cannot restore it.

**Arch couplings:** Limine snapshot menu; `limine-snapper-restore`;
`ryoku-pkg-aur-add` (AUR); `pacman -Q limine-snapper-sync` (`1323`).

**As-is on Debian:** PARTIAL — `--to` works once `Track` is ported; the snapshot
restore guide names tools Debian lacks. Port steps: §6.

### 1.4 `ryoku snapshots` (`main.go:59`, `update.go:1333-1348`)

**What it does:** requires `snapper` and `/etc/snapper/configs/root`; reads
`snapper -c root --csvout list --columns number,type,date,description,cleanup`
unprivileged, then via `sudo -n` (`1360-1370`), requires the CSV header
(`isSnapshotCSV` `1376-1383`, because snapper exits 0 with "No permissions.");
falls back to `sudo snapper -c root list` (`1344`); prints rows, free space, and
"listed in the Limine boot menu" iff `pacman -Q limine`,
`pacman -Q limine-snapper-sync` and the unit is enabled (`1458-1462`).

**As-is on Debian:** PARTIAL — snapper 0.10.6 (trixie, forky, sid, resolute)
prints the same CSV; only `snapshotsInBootMenu` is Arch/Limine-specific.
`docs/cli.md:91` says it runs `sudo snapper list`; the code tries unprivileged
first.

### 1.5 `ryoku track <stable|testing|unstable-dev|main|v<tag>> [--source]` (`main.go:73`, `track.go:27-110`)

**What it does:** `--source` + `main|unstable-dev` runs `bin/ryoku-track` from
the checkout or downloads it from
`https://raw.githubusercontent.com/ryoku-dev/ryoku-arch/main/bin/ryoku-track`
(`track.go:16,91-110`); that script runs
`sudo pacman -S --needed --noconfirm git go cmake ninja qt6-shadertools wayland base-devel matugen`
(`bin/ryoku-track:36`). Otherwise maps `unstable-dev→testing`, `main→stable`
(`track.go:73-84`) and calls `updater.Track` (`release.go:126-174`): refuses an
unknown channel, a box with neither `ryoku-desktop` nor a `[ryoku]` stanza, or a
private mirror (`127-141`); short-circuits when already on the channel and its
`release.json` names the installed release (`144-151`); else
`switchToPackageChannel` (`180-191`: retire source tracking
`sys/repo.go:92-148`, rewrite the `[ryoku]` `Server =` line with `sudo install`
and drop `/var/lib/pacman/sync/ryoku.*`, `sys/release.go:130-186`), clears
`RYOKU_CHANNEL` from the user manager (`systemctl --user unset-environment`,
`dbus-update-activation-environment`, `release.go:202-206`), then
`Update(--channel-switch)` (`release.go:196`).

Channel ↔ server map (`sys/release.go:28,55-90`): stable =
`https://repo.ryoku.dev/stable/$arch`, testing = `.../channels/testing/$arch`,
`v<tag>` = `.../releases/<tag>/$arch`.

**As-is on Debian:** NO. Port: §8 I-12 (channel handling on apt).

### 1.6 `ryoku boot-guard [--disarm]` (`main.go:57`, `bootguard.go:94-126`)

**What it does:** root-only (`95-97`), run by
`ryoku/cli/systemd/ryoku-boot-guard.service` (`Before=display-manager.service`,
`ConditionPathExists=/var/lib/ryoku/update-pending.json`). Reads the marker
stage 2 wrote (`70-91`); a session's `/var/lib/ryoku/boot/ok-<uid>` from a later
boot disarms (`128-142`); boot 2 → `revertRelease` (`157-181`: rewrite the
channel to the previous tag, `nm-online -q --timeout=90`,
`pacman -Syy --noconfirm`,
`env SNAP_PAC_SKIP=y pacman -S --noconfirm --overwrite <glob> ryoku-desktop`,
`runuser -u <user> -- env HOME=... ryoku materialize` for each
`/home/*/.config/ryoku` `186-193`, notice JSON); boot 3 →
`pointBootMenuAtSnapshot` (`199-224`) rewrites `default_entry:` in
`/boot/limine.conf` to the `Snapshots/<title>/<kernel>` entry whose cmdline
carries `subvol=/@snapshots/<id>/snapshot` (`229-250`).

**As-is on Debian:** NO. **Port steps:**

1. `revertRelease`: `apt-get update --error-on=any` (retry-next-boot semantics
   at `165-171` need a non-zero exit on fetch failure, which apt only gives with
   `--error-on=any`); then install the full served set at the target versions
   (same argv as §1.1 install step) rather than only `ryoku-desktop`: apt
   satisfies `ryoku-desktop`'s `=`-pinned depends by downgrading only when each
   dependency's candidate is the target version.
2. `pointBootMenuAtSnapshot`: Limine branch kept only if Limine is kept (boot
   chain doc). GRUB branch: `grub-reboot '<grub-btrfs submenu>><entry>'` or
   `GRUB_DEFAULT=saved` + `grub-set-default`; grub-btrfs titles its entries from
   `/etc/default/grub-btrfs/config` (`GRUB_BTRFS_SUBMENUNAME`, default
   "`<distro>` snapshots") — the entry path parser (`229-250`) is rewritten
   against `/boot/grub/grub-btrfs.cfg`.
3. `runuser` is `/usr/sbin/runuser` on Debian (root's PATH has it).
4. Unit and tmpfiles ship via `dh_installsystemd`/`dh_installtmpfiles`; Debian
   enables the unit at install (`deb-systemd-helper`), the doctor's enable step
   (`reconcile_bootguard.go:54`) becomes a no-op.

### 1.14 Ryotunes external channel (`internal/ryotunesrelease/`, called from `update.go:149,781`, `ryotunes.go:26-60`, doctor `reconcile_ryotunes.go`)

**What it does:** GitHub release of `ryoku-dev/ryotunes` (`client.go:37`) via
`https://api.github.com` (`client.go:97`); the asset must be exactly
`ryotunes-<X.Y.Z>-<rel>-x86_64.pkg.tar.zst` + `.sha256` (`discover.go:54-118`);

(`ryotunesrelease.go:42-52`), arch `x86_64` (`:40`); `vercmp` ordering
(`client.go:290-299`); install = root `mktemp -d /var/tmp/ryotunes-release.X`,

(`client.go:214-242`). The `[ryoku]` repo also re-signs and serves the same
`.pkg.tar.zst` (`release/repo/import-ryotunes.sh:1-30`,
`release/repo/build-repo.sh:202-204`); the update set excludes `ryotunes`
(`ryokuset.go:49`).

**As-is on Debian:** NO — the upstream asset is an Arch package (`v1.2.1`:
`ryotunes-1.2.1-1-x86_64.pkg.tar.zst`, plus a source tarball
`ryotunes-1.2.1.tar.gz`, checked with `gh api`).

**Port steps (two variants, human decision Q-4):**

- (a) Keep a separate channel: the port builds `ryotunes_<ver>_amd64.deb` from
  `ryotunes-<ver>.tar.gz` and publishes it with a `.sha256` on its own release
  page; client changes: asset regex → `ryotunes_<X.Y.Z>-<rel>_amd64.deb`,
  `wantArch` → `amd64`, identity via
  `dpkg-deb -f <file> Package Version Architecture`, installed version via
  `dpkg-query -W -f='${Version}'`, install via
  `apt-get install -y /var/tmp/ryotunes-release.X/<file>.deb` (plain `dpkg -i`
  does not pull dependencies), ordering via `dpkg --compare-versions`; epoch
  `1:` survives unchanged in Debian syntax.
- (b) Drop the external channel: delete `externalReleasePkgs`
  (`ryokuset.go:49`), the `upgradeRyotunes`/`addRyotunesUpdate` calls
  (`update.go:149,781,1579`), `reconcileRyotunes`, and ship `ryotunes` in the
  Ryoku apt repo like any other package.

## 4. materialize and the user_edits overlay

### materialize (`internal/updater/materialize.go:156-333`)

**What it does:**

1. Base = `sys.BaseConfigDir()`: `$RYOKU_CONFIG_BASE`, else
   `/usr/share/ryoku/config` (`internal/sys/fsops.go:12-17`). Missing base:
   error telling a checkout to use `ryoku deploy` (`materialize.go:162-169`).
2. Ensures `~/.config/ryoku` exists (`175`), walks every regular file of the
   base (`177`, `walkRel` `346-366`).
3. Seeds (`generatedSeed` `39-57`, plus the whole `nvim/` tree, `63-65`) are
   copied only when the slot is empty, tested with `Lstat` so a user's dangling
   symlink counts as filled (`202-213`).
4. Any other file: if its live bytes match neither the last-laid hash nor the
   shipped hash, the live file is copied into the overlay as a fork first
   (`214-230`); then the shipped file is copied atomically (`231-234`,
   `sys.CopyFile` temp+rename, `fsops.go:33-59`).
5. Prunes: `~/.config/quickshell` is converged against the base wholesale
   (`251-261`); withdrawn `wireplumber/wireplumber.conf.d/NN-ryoku-*.conf`
   drop-ins go (`265-276`); files in the previous manifest and absent now go,
   except `mimeapps.list` (`284`) and whole trees of a provider the base no
   longer ships (switched-away compositor, `292-308`).
6. Lays the overlay last (`309`, `overlayUserEdits` `428-447`), skipping
   live-owned files.
7. Records `path<TAB>sha256` for every managed file in
   `~/.local/state/ryoku/materialized` (`310-318`, `writeManifest` `412-424`).
8. `systemctl --user try-restart wireplumber.service` when the Bluetooth policy
   or a drop-in changed (`320-323`).
9. Renders each laid compositor tree's generated half through
   `ryoku-wm-<name> apply ~/.config/ryoku/desktop.json` when it is missing
   (`applyGenerated` `112-139`).

### user_edits (`internal/sys/useredits.go`, `internal/updater/reset.go`)

- Overlay root `~/.config/ryoku/user_edits` (`fsops.go:25-27`); layable files =
  regular files, not symlinks, not `*.md`, not nested `ryoku/user_edits/`
  (`useredits.go:17-43`).
- Live-owned files never come from the overlay: `kitty/user.conf`,
  `fastfetch/config.jsonc`, `kitty/current-theme.conf`, `ghostty/ryoku-colors`,
  every provider's `wm.ConfigUserOwned`, and `nvim/` (`useredits.go:51-84`).
  `reconcileUserEdits` moves stale copies out (§3a).
- `ryoku reset [path] [-y]` deletes overlay files (all after a confirm), removes
  the live copy on a packaged box, and re-runs `Materialize` (`reset.go:23-94`).

**Is it distro-neutral?** YES. It is pure Go file I/O plus one user-unit restart
and the provider binary. It execs nothing distro-specific, reads no package
database, and its only system path is the base tree.

**What lays the base tree:** `ryoku-desktop` `package()`
(`release/packages/ryoku-desktop/PKGBUILD:250-540`;
`local cfg="$pkgdir/usr/share/ryoku/config"` at `:252`; the quickshell and Hub
trees at `:268-275`; app trees in the loop that follows), plus each compositor
variant: `ryoku-desktop-hyprland/PKGBUILD:51` and
`ryoku-desktop-niri/PKGBUILD:47` (same `cfg` variable). On Debian the same three
packages must install the same tree under `/usr/share/ryoku/config`.

**Debian notes:**

1. Files under `/usr/share` are never conffiles, so dpkg will not prompt or keep
   `.dpkg-dist` copies; the base must stay out of `/etc`.
2. When a compositor variant .deb is removed, dpkg deletes its files from
   `/usr/share/ryoku/config/<dir>`. That is the signal `keepsSwitchedAwayTree`
   relies on (`materialize.go:84-90`); it works the same.
3. Some materialized _content_ does not behave the same on Debian. For example,
   `~/.config/chromium-flags.conf` is shipped and laid (test
   `materialize_test.go:420-433`), but Debian's `/usr/bin/chromium` wrapper
   sources only `/etc/chromium.d/*` (chromium 150.0.7871.181-1~deb13u1
   `debian/scripts/chromium:76-77`) and `$CHROMIUM_FLAGS`. Arch's launcher reads
   the XDG file, so these flags have no effect on Debian. Other content is
   covered in the config/theming docs.
4. `ryoku-desktop` is `arch=('x86_64')` because it compiles Go helpers
   (`PKGBUILD:14-15`). An `Architecture: amd64` .deb carrying `/usr/share` data
   is valid; lintian reports only an informational tag.

## 6. Snapshots and rollback: snapper + Limine today, Debian equivalents

### What the Arch build couples together

1. `ryoku update` brackets its own transaction with one snapper pre/post pair
   (`update.go:1789-1819`) and passes `SNAP_PAC_SKIP=y` (`ryokuset.go:234`) so
   snap-pac does not add a second pair. Plain `pacman` transactions are
   snapshotted by snap-pac (`update.go:1154-1159`).
2. limine-snapper-sync (`/usr/lib/snapper/plugins/10-limine-snapper-sync`,
   `limine-snapper-sync.service` = `limine-snapper-watcher`, the
   `snapper-cleanup.service.d/limine-snapper-override.conf` drop-in with
   `ExecStopPost=limine-snapper-sync --no-force-save`;
   `release/packages/limine-snapper-sync/PKGBUILD:83-84`) writes a `//Snapshots`
   tree into `/boot/limine.conf` and copies the matching kernels to the ESP.
3. Restore runs from the boot menu: boot the snapshot, run
   `sudo limine-snapper-restore` (`update.go:1306-1330`). `snapper rollback` is
   unusable because the root is pinned `rootflags=subvol=@`
   (`update.go:1231-1237`).
4. The boot guard's last resort points `default_entry` at that snapshot's entry
   (`bootguard.go:199-250`).
5. Pruning: the update path runs `snapper cleanup number` (`update.go:1818`).
   The comment there and `reconcile_snapshots.go:18-24` say the timer route is
   unreliable because snapper-cleanup's success is coupled to
   limine-snapper-sync's `ExecStopPost`.

### Debian facts

- `snapper` 0.10.6 is in trixie (0.10.6-1.2), forky/sid (0.10.6-1.3+b1) and
  resolute (0.10.6-1.3). It ships `/etc/apt/apt.conf.d/80snapper`,
  `/etc/default/snapper`, `snapper-{boot,cleanup,timeline}.{service,timer}` and
  `snapperd` (packages.debian.org file lists for trixie/forky/sid;
  packages.ubuntu.com for resolute).
- `80snapper` (snapper `debian/80snapper`, verbatim):

  ```text
  DPkg::Pre-Invoke  { "if [ -e /etc/default/snapper ]; then . /etc/default/snapper; fi; if [ -x /usr/bin/snapper ] && [ ! x$DISABLE_APT_SNAPSHOT = 'xyes' ] && [ -e /etc/snapper/configs/root ]; then rm -f /var/tmp/snapper-apt || true ; snapper create -d apt -c number -t pre -p > /var/tmp/snapper-apt || true ; snapper cleanup number || true ; fi"; };
  DPkg::Post-Invoke { "if [ -e /etc/default/snapper ]; then . /etc/default/snapper; fi; if [ -x /usr/bin/snapper ] && [ ! x$DISABLE_APT_SNAPSHOT = 'xyes' ] && [ -e /var/tmp/snapper-apt ]; then snapper create -d apt -c number -t post --pre-number=`cat /var/tmp/snapper-apt` || true ; snapper cleanup number || true ; fi"; };
  ```

  It runs only when apt drives dpkg, not for a bare `dpkg -i`.

- `/etc/default/snapper` as shipped (`data/sysconfig.snapper`, installed by
  `debian/rules`): `SNAPPER_CONFIGS=""` and `DISABLE_APT_SNAPSHOT="no"`. snapper
  is configured `--with-conf=/etc/default` (`debian/rules`), so
  `SNAPPER_CONFIGS` is read from this file, not `/etc/conf.d/snapper`.
  `snapper-cleanup.service` runs `/usr/lib/snapper/systemd-helper --cleanup`
  over `SNAPPER_CONFIGS`.
- `snapper-boot.timer` (`OnBootSec=1`, `WantedBy=timers.target`) and
  `snapper-boot.service`
  (`snapper --config root create --cleanup-algorithm number --description "boot"`,
  `ConditionPathExists=/etc/snapper/configs/root`) ship in the package. Debian's
  debhelper enables timers at install (`debian/changelog` 0.3.3-0.2: "set 10 to
  enable systemd service by default"), so a Debian box takes a `boot` snapshot
  every boot once the root config exists.
- Not packaged in any Debian or Ubuntu suite (sources.debian.org `api/search`
  returns `exact: null` and `tools/pkgver` prints `-` everywhere): `snap-pac`,
  `limine`, `limine-snapper-sync`, `grub-btrfs`. Ubuntu resolute has
  `apt-btrfs-snapshot` 4.0.1build1, a different snapshot mechanism
  (`@apt-snapshot-*` subvolumes), not installed by default.

### Equivalent of `SNAP_PAC_SKIP=y` (one pair per `ryoku update`)

`80snapper` sources `/etc/default/snapper` after the environment is set, and
that file sets `DISABLE_APT_SNAPSHOT="no"`, so
`sudo env DISABLE_APT_SNAPSHOT=yes apt-get ...` is overwritten. The options
(decision Q-5):

| Option | Mechanism                                                                                                                                                                  | Consequence                                                                                                                                                                                                                                                                   |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A      | doctor/installer edits `/etc/default/snapper` to `DISABLE_APT_SNAPSHOT="${DISABLE_APT_SNAPSHOT:-no}"`; `ryoku update` runs `sudo env DISABLE_APT_SNAPSHOT=yes apt-get ...` | one pair per update, as on Arch. The file is a conffile, so the next snapper upgrade that changes it prompts (or keeps the edit with `--force-confold`). snapper's own parser also reads this file; how it treats a `${...}` value for a key it does not use was not verified |
| B      | the Ryoku package `dpkg-divert`s `80snapper` and ships a replacement that honours an environment variable                                                                  | one pair per update; Ryoku owns a copy of snapper's hook                                                                                                                                                                                                                      |
| C      | drop Ryoku's own pre/post (`update.go:134-136,788`) and keep 80snapper's                                                                                                   | one pair per apt run, described `apt` instead of `ryoku-update (from <sha>)`. The boot guard and the rollback hint need the pre number: read `/var/tmp/snapper-apt`, which 80snapper leaves in place                                                                          |
| D      | keep both                                                                                                                                                                  | four snapshots per update (two Ryoku, two apt), each followed by `snapper cleanup number`. With `NUMBER_LIMIT="10"` (`doctor.go:473`), the retained history covers about half as many updates                                                                                 |

### Rollback/restore path (follows the boot-chain decision, Q-2)

- **(a) Keep Limine.** Package `limine` (upstream v12.9.3; build deps clang,
  lld, llvm, nasm and mtools exist in all suites), `limine-entry-tool` 1.37.1
  and `limine-snapper-sync` 1.31.0. Both tools are GraalVM native images: build
  per target suite (glibc 2.41 trixie, 2.43 forky/sid/resolute) with the
  vendored GraalVM 25 + Gradle 9.6.1, as the PKGBUILDs do (Debian's gradle is
  4.x, and openjdk-25 has no native-image). Debian glue the port writes:
  - `/etc/kernel/postinst.d/zz-ryoku-limine`:
    `limine-entry-tool --add-kernel|--add-uki`, keeping the
    `comment: Kernel version:` line that `reconcile_limine_images.go:104`
    parses.
  - `/etc/kernel/postrm.d/zz-ryoku-limine`.
  - `/etc/initramfs/post-update.d/ryoku-limine`.
  - A `DPkg::Pre-Invoke` replacement for limine-snapper-sync's libalpm lock
    hook.

  limine-snapper-sync needs no pacman (its watcher's pacman-lock cleanup is
  inert). `limine-snapper-restore`, `restoreGuide` and `pointBootMenuAtSnapshot`
  stay as they are. Secure Boot: Limine is not signed by the Debian/Microsoft CA
  chain, and limine-entry-tool signs only via `sbctl`, which no suite packages.

- **(b) GRUB + grub-btrfs.** Package grub-btrfs v4.14 from upstream
  (`make install DESTDIR=... PREFIX=/usr SYSTEMD=true INITCPIO=false GRUB_UPDATE_EXCLUDE=true`;
  Depends `btrfs-progs`, `grub-common`, `gawk`, `inotify-tools`; Kali's
  `debian/` dir at gitlab.com/kalilinux/packages/grub-btrfs is a reference). It
  installs `/etc/grub.d/41_snapshots-btrfs`, `/etc/default/grub-btrfs/config`
  and `grub-btrfsd.service`. grub-btrfs has no restore tool, so `restoreGuide`
  (`update.go:1306-1330`) needs one of:
  - a Ryoku-authored restore helper that, from the booted snapshot, creates `@`
    anew from `/.snapshots/<id>/snapshot` and moves the old `@` aside. This is
    the pinned-`subvol=@` equivalent of `limine-snapper-restore`.
  - a switch to a `snapper rollback`-compatible layout (no `subvol=` pin on the
    cmdline or in fstab, default subvolume set by snapper). `restoreGuide` would
    then print `sudo snapper rollback <id>`. This changes the installer's layout
    (another doc).

  Two more limits under (b):
  - Snapshots are read-only, and grub-btrfs ships an overlay hook only for
    mkinitcpio, with dracut via `rd.live.overlay.overlayfs=1`; initramfs-tools
    has none. Booting a snapshot read-only must therefore be tested.
  - Per-snapshot kernels are used only when `/boot` is inside the btrfs root.

- **CLI changes either way:**
  - `gatherSnapHelpers`/`wantedSnapperHelpers`/`offerSnapperHelpers`
    (`update.go:1119-1189`): drop snap-pac (80snapper is part of `snapper`);
    offer the boot-menu sync package of the chosen variant via `apt-get install`
    (not `ryoku-pkg-add`, which sysupgrades on Arch).
  - `snapshotsInBootMenu` (`update.go:1458-1462`): (a) dpkg probes; (b)
    `grub-btrfsd.service` enabled + `/etc/grub.d/41_snapshots-btrfs` executable.
  - `reconcileSnapper` path and probe fixes (§3a).
  - `snapper-boot.timer` handling (Q-6).
  - `pointBootMenuAtSnapshot` per §1.6.

## 8. Issues / risks

- **I-1 Version ordering.** `vercmp` (rpmvercmp) and dpkg differ: pacman ranks a
  letter segment below end-of-string (`1.0rc1 < 1.0`); dpkg ranks it above
  (`1.0rc1 > 1.0`) and uses `~` for pre-releases. Ryoku's own
  `<core>.r<count>.g<sha>-<rel>` (`bin/ryoku-release-version:30-43`) sorts the
  same under both, because `r<count>` increases monotonically. Upstream versions
  the port repackages (e.g. zen `1.23.2b`) must be mapped to Debian form, e.g.
  `1.23.2~b`. Epochs: ryotunes' `1:` survives (`ryotunesrelease.go:42-52`);
  `version.go:98` breaks on any epoch.
- **I-2 Partial upgrades.** The Arch Ryoku lane (`pacman -Sy` then
  `pacman -S <targets>` without `-u`, `ryokuset.go:213-237`) is a partial
  upgrade, which Arch does not support. Debian supports one. Expected apt
  behaviour: installing a newer Ryoku package pulls the newer Debian
  dependencies it needs in the same transaction. It fails if such a dependency
  is held, pinned below the needed version, or only in backports (NotAutomatic,
  priority 100).
- **I-3 Held packages.** With `apt-mark hold`, `apt-get install -y` aborts
  ("Held packages were changed and -y was used without
  --allow-change-held-packages"). pacman with an explicit target on `IgnorePkg`
  asks and `--noconfirm` answers yes. A self-built Hyprland stack is typically
  held (`apt-mark hold`) to stop Debian's libxkbcommon evicting it. If the Ryoku
  repo serves held names, the update must pass `--allow-change-held-packages`,
  or skip and report them (Q-7).
- **I-4 Backports.** Hyprland is in trixie only via trixie-backports
  (0.55.2+ds-1~bpo13+1), and quickshell too (0.3.0-1~bpo13+1). On trixie, Ryoku
  debs depending on bpo versions need `-t trixie-backports`, or a pin for those
  names. Otherwise apt reports unmet dependencies (backports have priority 100
  and are not candidates).
- **I-5 Exit codes.** `apt-get update` exits 0 when fetches fail (only `W:`)
  unless `--error-on=any`. The boot guard's "retry next boot"
  (`bootguard.go:165-171`) and the update's refresh failure log
  (`update.go:175-177`) depend on a non-zero exit.
- **I-6 dpkg file semantics vs pacman's `--overwrite`.**
  - dpkg replaces a file no package owns without complaint, so
    `ryokuOverwriteGlob`, `unownedFiles`, `healPackageUpgrade`'s strays branch
    and `reconcileConflictingRyokuFiles` are unnecessary for non-conffiles.
  - A file owned by another package fails with
    `trying to overwrite '<path>', which is also in package <p>`. The fix is
    `Replaces:`/`Breaks:` in packaging; `--force-overwrite` is the CLI escape.
  - Every file under `/etc` in a .deb is a conffile (dh_installdeb). An unowned
    pre-seeded copy that differs makes dpkg prompt. With
    `--force-confdef --force-confold` it keeps the seed and writes `.dpkg-dist`,
    which reconcilePacnew's Debian rewrite must find.
  - Non-interactive runs also need `DEBIAN_FRONTEND=noninteractive` (debconf).
    On Ubuntu, `needrestart` (installed by default) prompts unless
    `NEEDRESTART_MODE=a` or `NEEDRESTART_SUSPEND=1`. `apt-listchanges` pages
    news on a TTY unless `APT_LISTCHANGES_FRONTEND=none`.
- **I-7 Output scraping.** The curated view and conflict collection parse
  pacman's English text (`upgradelog.go:514-552`). apt and dpkg messages are
  translated; use `LC_ALL=C` or `-o APT::Status-Fd=<fd>`. The Hub reads only the
  run-state JSON (`runstate.go`), so it is unaffected.
- **I-8 Locks.** There is no stale-lock equivalent: dpkg/apt locks are `fcntl`
  locks and the lock files must never be deleted (`update.go:1104-1114` and
  `doctor.go:826-840` have no Debian port). The crash residue to heal is an
  interrupted dpkg (`dpkg --audit`, `dpkg --configure -a`) and broken
  dependencies (`apt-get check`, `apt-get -f install`).
- **I-9 The delivery contract's "main fast-forward".** Three sources disagree:
  - `AGENTS.md:64-71` (rule 8) says "work reaches users only once `main`
    fast-forwards".
  - `bin/ryoku-dev-verify-delivery:7-8,86-96` says "the [ryoku] repo publishes
    on push to main".
  - The code and docs say otherwise:
    `.github/workflows/publish-repo.yml:13-19,24-30` triggers on push to
    `unstable-dev` (testing) and on `v*` tags (stable); a push to `main`
    "publishes nothing". `docs/updates.md:307-316` agrees. For the port, the
    human's CI decides which branch/tag feeds which apt suite. The
    verify-delivery publish-lag check (`:86-96`, which compares `origin/main`
    with `origin/unstable-dev`) and the AGENTS.md rule need rewording to match
    whatever trigger the port's CI uses.
- **I-10 Delivery gate scope.** `ryoku-dev-verify-delivery` counts a config as
  delivered when a PKGBUILD, `installation/backend/lib/deploy.sh` or
  `ryoku/shell/deploy.sh` names it (`:25-38`). It also requires
  `usr/share/ryoku/i18n` in one of them (`:78-83`). The port's
  `debian/*.install` / `debian/rules` must be added to `sources`, or every
  Debian-only delivery path reads as an orphan.
- **I-11 Two lanes on apt.** The user's `sudo apt full-upgrade` moves the Ryoku
  packages too whenever the Ryoku repo serves newer versions. The same holds for
  `pacman -Syu` on Arch, so the contract is unchanged. `unattended-upgrades`
  (2.12 trixie, if installed) only touches origins in
  `Unattended-Upgrade::Origins-Pattern`; the Ryoku origin is excluded unless
  added.
- **I-12 Channel handling on apt.** Today the channel is the `Server` URL path:
  `x86_64/` (stable, a byte copy of the newest release),
  `channels/testing/x86_64/`, `releases/<tag>/x86_64/`
  (`internal/sys/release.go:15-28,55-90`). Two apt layouts map onto it:
  - (A) **flat repo per directory.** `URIs: <base>/` (or
    `<base>/channels/testing/`, `<base>/releases/<tag>/`) and `Suites: ./`, with
    no `Components:` (sources.list(5) exact-path form). This mirrors today's
    layout 1:1, keeps `release.json`/`manifest.json` beside the index, and keeps
    `ChannelOfServer` a URL parse.
  - (B) **one pool with `dists/<suite>`** (reprepro 5.4.6 / aptly 1.6.x in all
    suites). The channel is the `Suites:` value (`stable`, `testing`,
    `v0.75.5-beta.20`), the pool dedupes .debs across frozen releases, and
    `ChannelOfServer` parses Suites.

  Either way:
  - **The stable pointer cannot be a byte copy of a release's
    `Release`/`InRelease`.** apt refuses a repository whose
    `Codename`/`Origin`/`Label` changed until confirmed
    (`--allow-releaseinfo-change`, apt-secure(8)). The stable index must keep
    constant `Origin`/`Label`/`Codename`, or the CLI must pass
    `--allow-releaseinfo-change-codename`.
  - **A channel move is a rewrite of `ryoku.sources` plus `apt-get update`.**
    List files are named after the URI, so pacman's stale-db/signature wedge
    (`sys/release.go:163-186`) does not occur.
  - **Moving down needs `--allow-downgrades` with explicit `<p>=<v>` targets.**
    The alternative is `Pin-Priority: 1001` for the Ryoku origin in
    `/etc/apt/preferences.d/`, which makes every apt run (the user's lane
    included) prefer Ryoku's versions, downgrades included (Q-3).
  - **Suite × base matrix.** One Arch x86_64 build serves Arch and CachyOS
    (`docs/updates.md:293-297`). Debian .debs built against trixie libraries are
    not installable on forky or resolute (different `libqt6*`/`libc6` ABIs), so
    the repo needs a base-codename dimension (e.g. `Suites: stable-trixie`).
    `ChannelServer`/`ChannelOfServer`/`ChannelURL` must carry it.
  - **Keyring.** `Signed-By: /usr/share/keyrings/ryoku-archive-keyring.pgp`
    replaces `SigLevel = Required`
    - `pacman-key --populate`. apt 3.0 verifies with `sqv`, which rejects SHA-1
      and DSA. Ryoku's current release key is Ed25519
      (`keys/ryoku-release-key.pub.asc`, algo 22).

- **I-13 `hasPacman` gate.** `sys.Has("pacman")`
  (`reconcile_shipped_apps.go:88`) is the "is this a package box" test for three
  reconcilers. Debian's `pacman-package-manager` (7.0.0-1+b1 trixie) installs
  `/usr/bin/pacman`. Without pacman they silently report ok; with that package
  they run pacman against an empty Arch database.
- **I-14 `/etc/ryoku-release` becomes a conffile.** `ryoku-desktop` writes it
  per build (`PKGBUILD:259-266`). Under `/etc` in a .deb, dh_installdeb marks it
  a conffile:
  - a user-deleted copy is not restored on upgrade;
  - it survives `remove` (until purge);
  - a local edit makes every upgrade prompt.

  The CLI reads it via `sys.ReleaseFile` (`internal/sys/release.go:41`).
  Shipping it as `/usr/lib/ryoku/release` (and pointing `ReleaseFile` there)
  keeps it package-owned and always current. The same applies to
  `/etc/systemd/logind.conf.d/10-ryoku-lid.conf` (I-6).

- **I-15 "explicit" vs "manual".** `ryoku verify`'s `Extra` list is
  `pacman -Qqe` minus manifest names (`manifest.go:275-297`). Debian's
  installer, debootstrap and tasksel mark the base as manual, so
  `apt-mark showmanual` reports hundreds of base packages as "added by you". The
  manifest's base lane must name the Debian base set, or `Verify` must subtract
  `priority: required/important` packages.
- **I-16 Kernel lane on Debian.** Debian kernels arrive through the
  `linux-image-amd64` meta and trixie-security in the user's lane, as versioned
  packages, with several kept installed (`/etc/apt/apt.conf.d/01autoremove`
  `VersionedKernelPackages`). The Ryoku lane still never moves them.
  `reportSystemLane`'s "kernel included" text (`update.go:409`) stays accurate.
- **I-17 Status freshness.** `checkupdates` syncs a private database on every
  status poll (`update.go:1701-1711`). The apt equivalents read lists that are
  only as fresh as the last `apt-get update`. The shell daemon polls
  `ryoku status --json` on a cadence (`ryoku/shell/ipc/updates.go:15,71`), so
  freshness needs either the private-tree refresh or a periodic system refresh
  (Q-9).
- **I-18 Bugs and dead code found (pre-existing, distro-neutral):**
  - `healPackageUpgrade` is called twice (`update.go:215,220`);
  - an unreachable error check (`update.go:192-196`);
  - `channelSwitchArgs` has no caller (`update.go:532-535`);
  - the `readFileSafe` guards never fire (`reconcile_limine.go:680,786`;
    `doctor.go:2537,2721`);
  - `ryoku-pkg-add` sysupgrades inside the Ryoku lane

## Questions for the human

- **Q-1 One codebase or a fork?**
  - (a) Fork: replace pacman with apt in place. This is the smallest diff, but
    the Debian tree diverges from upstream Ryoku on every package-touching file.
  - (b) Dual: `internal/sys/pkg_{pacman,apt}.go` behind a `debian` build tag,
    plus distro-specific reconcilers behind the same tag. The upstream-merge
    surface is smaller, but every Arch-specific reconciler needs a tagged twin
    or a skip.
- **Q-2 Boot chain: Limine or GRUB?**
  - (a) Limine: package limine, limine-entry-tool and limine-snapper-sync
    (GraalVM native builds per suite) and write Debian kernel hooks; the
    rollback UX stays identical; Secure Boot via the Debian shim chain is lost.
  - (b) GRUB + grub-btrfs: package one shell project; Secure Boot works with
    shim-signed and grub-efi-amd64-signed; a restore helper must be written or
    the subvolume layout changed; the boot guard, `restoreGuide` and five
    reconcilers are rewritten.
- **Q-3 Repo layout and downgrade mechanism.**
  - Layout: (A) flat per-directory repos (1:1 with today's URLs) or (B) a
    reprepro/aptly pool with suites.
  - Downgrades: explicit `<p>=<v> --allow-downgrades` (only `ryoku update` moves
    the set down) or an origin pin at 1001 (every apt run prefers Ryoku's
    versions, downgrades included).
- **Q-4 Ryotunes.** (a) Keep a separate GitHub-release channel with a `.deb`
  asset contract the port publishes itself (the upstream `ryoku-dev/ryotunes`
  publishes only `.pkg.tar.zst`). (b) Fold it into the apt repo and delete the
  external channel code.
- **Q-5 Snapshot pair per update.** Options A–D in §6: edit
  `/etc/default/snapper`, divert `80snapper`, use 80snapper's pair only, or
  accept four snapshots per update.
- **Q-6 `snapper-boot.timer`.** Debian enables it, giving one `boot` snapshot
  per boot that counts against `NUMBER_LIMIT="10"`. Disable it in
  `reconcileSnapperCleanup`, or keep it.
- **Q-7 Held packages.** Pass `--allow-change-held-packages` in the Ryoku lane
  (matches pacman's explicit- target behaviour), or skip held names and report
  them.
- **Q-8 Cadence of formerly-AUR apps.** Ship zen/localsend/voxtype in the frozen
  release (they update only on a tag), or in a separate rolling suite outside
  the release freeze (another channel dimension for the CLI).
- **Q-9 Status freshness.** A private apt tree refreshed by `ryoku status` (no
  root; network on each poll, bounded like `checkupdates` at 120 s,
  `update.go:1709`), or `APT::Periodic::Update-Package-Lists "1"`
  (apt-daily.timer twice a day, root).

- `/usr/share/ryoku/config` (materialize base), `/usr/share/ryoku/i18n`
  (`main.go:42`, `ryoku-desktop/PKGBUILD:335,543-548`),
  `/usr/share/ryoku/lockscreen/*`, `/usr/share/ryoku/ryodecors`,

  (`update.go:248,1874-1879` prefers `/usr/bin`).

  `ryoku/shell/ipc/updates.go:71` and the Hub (`Singletons/Updates.qml`). The

  `UpdatesPage.qml`.

  (`ryoku/hub/quickshell/pages/UpdatesPage.qml:595`). The Profile plate reads
  `/var/log/pacman.log` for the install date
  (`ryoku/hub/quickshell/pages/ProfilePage.qml:47`; `stat -c %W /` is tried
  first).
- Installer/packaging must not seed `/etc` paths a package later owns (conffile
  prompt, I-6). Ship the release marker outside `/etc` (I-14).
- libalpm hooks (`94/95-ryoku-power-cutover`, the NVIDIA guard hook, limine
  hooks, limine-snapper-sync's lock hook) all become preinst/postinst, dpkg
  triggers, `/etc/kernel/postinst.d` or `DPkg::Pre/Post-Invoke` (§2 row 63, §3c,
  §6).
- The pacman install scriptlet's `RYOKU_MANAGED_UPDATE` deferral
  (`ryoku-desktop.install:118-140`) exists because libalpm cannot run a newly
  extracted hook; dpkg runs the new version's maintainer scripts, so the Debian
  postinst can adopt sessions synchronously.
- `tools/pkgver` earlier printed `-` for contrib/non-free packages and for names
  containing `+`. All rows in this document were re-queried after the fixes,
  except the NVIDIA rows, which the hardware survey took from madison directly.
- `/usr/sbin` off the user PATH (I-20) affects every unprivileged exec of sbin
  tools across Ryoku (e.g. `iw`, `modinfo` in other components).
- Debian `/etc/vconsole.conf` is a symlink to `/etc/default/keyboard`, and
  localed's setters are denied by policy (§1.15). Any component that writes
  keyboard layout system-wide (installer, greeter, keyboard CLI) needs the
  console-setup route.
